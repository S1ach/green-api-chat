# Веб-чат MAX на GREEN-API

## О проекте

React-интерфейс для отправки и получения текстовых сообщений в мессенджере MAX через
[GREEN-API](https://green-api.com). Тестовое задание на позицию Frontend React-разработчика.

Пользователь вводит `idInstance` и `apiTokenInstance`, создаёт чат по номеру телефона, пишет
сообщение и видит ответы собеседника. Отправка идёт методом `SendMessage`, приём — по технологии
**HTTP API** (`ReceiveNotification` + `DeleteNotification`, без вебхуков). Бэкенда нет: браузер
обращается к GREEN-API напрямую.

## Возможности

- Подключение инстанса: `apiUrl`, `idInstance`, `apiTokenInstance` проверяются методом
  `getStateInstance`. Для состояний `notAuthorized`, `pendingPassword`, `starting`, `blocked` и других
  показывается подсказка, что делать.
- Создание чата по номеру телефона. Номер можно вводить в любом виде (`+7 999 123-45-67`,
  `8 (999) 123-45-67`, `79991234567`); `CheckAccount` подтверждает, что он есть в MAX, и отдаёт `chatId`.
- Отправка текстовых сообщений: `Enter` — отправить, `Shift+Enter` — новая строка. Сообщение
  появляется в чате после подтверждения API; при ошибке текст остаётся в поле для повторной отправки.
- Получение входящих сообщений последовательным опросом очереди уведомлений.
- Диалог: входящие слева, исходящие справа, время сообщения, автоскролл, который не мешает читать
  историю.
- Список чатов (`GetChats`) и история переписки (`GetChatHistory`) загружаются с сервера, поэтому
  видны и после перезагрузки страницы, и на другом компьютере. Счётчик непрочитанных, аватары (`GetAvatar`).
- Обработка ошибок: понятные сообщения для 400 / 401 / 403 / 429 / 466 / 5xx и сетевых сбоев,
  предупреждение, если настройки инстанса мешают приёму сообщений.
- Адаптивность: на экране уже 760 px видно либо список чатов, либо переписку.

## Использование

1. Создайте инстанс для мессенджера **MAX** в [console.green-api.com](https://console.green-api.com)
   и авторизуйте его по QR-коду (в MAX: Профиль → Устройства → «Войти по QR-коду»; пароль на вход
   в MAX нужно отключить, иначе QR-код не сработает).
2. Скопируйте `idInstance`.
3. Скопируйте `apiTokenInstance`. Если в консоли указан свой `apiUrl`, скопируйте и его.
4. Запустите приложение: `npm run dev`.
5. Введите учётные данные и нажмите «Войти».
6. Нажмите «+» → «Новый чат» и введите номер получателя.
7. Нажмите «Создать чат».
8. Напишите сообщение и нажмите `Enter`. Ответ собеседника появится слева в течение нескольких
   секунд без перезагрузки страницы.

### Настройка инстанса для приёма по HTTP API

Чтобы уведомления попадали в очередь, а не уходили на вебхук, в настройках инстанса должно быть:

- **webhookUrl** — пусто;
- **incomingWebhook** — `yes`.

Приложение само проверяет это методом `GetSettings` и показывает предупреждение, если настройки
мешают приёму. Изменения настроек применяются в течение нескольких минут.

## Архитектура

Проект разложен по слоям [Feature-Sliced Design](https://feature-sliced.design). Зависимости идут
только сверху вниз, слайсы подключаются через публичный API (`index.ts`); оба правила проверяет
ESLint (`no-restricted-imports` в [eslint.config.js](eslint.config.js)).

```text
src/
├── app/                      инициализация: store, глобальные стили, выбор страницы
│   ├── providers/store/      configureStore, сохранение состояния в localStorage
│   └── styles/               reset, CSS-переменные
├── pages/
│   ├── login/                экран подключения инстанса
│   └── chat/                 сайдбар + диалог, запуск приёма сообщений
├── widgets/
│   ├── sidebar/              Sidebar, SidebarMenu, ChatList
│   └── chat/                 Chat, ChatHeader, MessageList, автоскролл
├── features/
│   ├── configure-instance/   форма учётных данных, подключение и выход
│   ├── create-chat/          форма номера, CheckAccount
│   ├── send-message/         поле ввода, SendMessage
│   ├── receive-message/      цикл опроса очереди, проверка настроек инстанса
│   ├── load-chats/           GetChats и превью чатов
│   └── load-history/         GetChatHistory для открытого чата
├── entities/
│   ├── session/              учётные данные (slice)
│   ├── chat/                 чаты и сообщения (slice), аватар
│   └── message/              модель Message, разбор уведомлений и истории, MessageBubble
└── shared/
    ├── api/                  RTK Query: endpoints GREEN-API, baseQuery, схемы ответов, ошибки
    ├── config/               константы
    ├── lib/                  typed hooks, нормализация номера, хранилище, утилиты
    └── ui/                   Button, TextField, Loader, Alert
```

**Состояние.** В Redux лежит только то, что нужно нескольким частям приложения: учётные данные,
чаты, сообщения и открытый чат. Текст в поле ввода, значения форм и открытость меню — локальное
состояние компонентов. Серверное состояние (аватары, настройки инстанса) живёт в кэше RTK Query.

**API.** Все обращения к GREEN-API описаны в [src/shared/api/greenApi.ts](src/shared/api/greenApi.ts)
через `createApi` и `fetchBaseQuery`. Учётные данные — часть URL, поэтому адрес собирает `baseQuery`;
компоненты про токен не знают. Тело ответа проверяется Zod-схемой до того, как попадёт в приложение.

## Как устроен приём сообщений

```text
receiveNotification?receiveTimeout=5
        ↓
очередь пуста (null)? → сразу следующий receiveNotification
        ↓
parseIncomingNotification(body) → входящее текстовое сообщение или null
        ↓
сообщение → messageReceived → нужный чат в store
        ↓
deleteNotification/{receiptId}
        ↓
следующий receiveNotification
```

Реализация — [useNotificationPolling](src/features/receive-message/model/useNotificationPolling.ts):

- цикл один и строго последовательный: следующий запрос уходит только после обработки предыдущего;
- цикл останавливается при размонтировании страницы, выходе и смене учётных данных; запрос,
  который в этот момент в полёте, отменяется;
- каждое уведомление удаляется, даже нерелевантное (статусы, медиа, исходящие) — иначе очередь встанет;
- принимается только `incomingMessageReceived` с текстом (`textMessage`, `extendedTextMessage`,
  `quotedMessage`), остальное в чат не попадает;
- повторно доставленное уведомление не дублирует сообщение — проверка по `idMessage`;
- при ошибках — пауза от 1 до 30 секунд с экспоненциальным ростом и баннер в интерфейсе.

## Тесты

```bash
npm run test
```

- **API-слой** — URL и тела запросов, проверка формата ответов, тексты ошибок, повтор после 429.
- **Приём сообщений** — один цикл даже в StrictMode, удаление каждого уведомления, отсутствие дублей,
  остановка при размонтировании, повтор после ошибки.
- **Состояние** — сопоставление входящего сообщения с чатом, непрочитанные, слияние с историей,
  сохранение и восстановление из `localStorage`.
- **Разбор данных** — парсер уведомлений (неподдерживаемые типы не превращаются в сообщение),
  история, нормализация номера.
- **UI через поведение пользователя** — входящее и исходящее сообщение, запрет отправки пустого
  сообщения, `Enter` / `Shift+Enter`, сохранение текста при ошибке отправки, валидация форм, автоскролл.
- **Сценарий из ТЗ целиком** — подключение → новый чат → отправка → получение ответа → выход.

В тестах GREEN-API подменяется на уровне `fetch`; в самом приложении моков и имитации сообщений нет.

## Security

- Учётные данные **не хранятся в репозитории**: их вводит пользователь, в коде, тестах и README
  настоящих значений нет. Файлы `.env*` добавлены в `.gitignore`.
- Введённые данные сохраняются только в `localStorage` браузера и уходят исключительно в запросы
  к указанному `apiUrl`. Кнопка «Выйти» удаляет их.
- `apiTokenInstance` не попадает в логи: URL запросов не логируются, тексты ошибок формируются
  по HTTP-статусу.
- Бэкенда нет, поэтому токен доступен в браузере пользователя. Для продакшена его стоит спрятать
  за серверным прокси.

## Ограничения

- Поддерживаются только текстовые сообщения; файлы, изображения, голосовые, реакции и группы
  не отображаются.
- Приложение зависит от GREEN-API: его доступности, тарифа и лимитов частоты запросов.
- `ReceiveNotification` отдаёт только новые уведомления (в очереди они хранятся 24 часа).
  История берётся отдельным методом `GetChatHistory`: не больше 5000 сообщений и не глубже 3 месяцев.
- Очередь уведомлений у инстанса одна. Если открыть приложение в двух вкладках или параллельно
  читать очередь другим клиентом, каждое уведомление получит только один из них.
- Номера распознаются для России и Казахстана (`7…`) и Беларуси (`375…`).
- Статусы доставки и прочтения не отображаются.

## Деплой

- **Vercel** — в репозитории есть [vercel.json](vercel.json): команда сборки `npm run build`, каталог `dist`.
- **GitHub Pages** — workflow [.github/workflows/deploy.yml](.github/workflows/deploy.yml) при пуше
  в `master` запускает линт, проверку форматирования и типов, тесты и сборку, затем публикует `dist`.
  В настройках репозитория нужно включить **Settings → Pages → Source: GitHub Actions**.

GREEN-API разрешает запросы из браузера (CORS), прокси не нужен. Если запросы блокирует сеть или
расширение, для разработки есть запасной вариант: `VITE_USE_PROXY=1 npm run dev` и `apiUrl = /green-api`
в форме входа (см. [vite.config.ts](vite.config.ts)).
